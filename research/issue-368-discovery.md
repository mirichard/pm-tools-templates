## Decision brief

Recommend that the owner consider one bounded first delivery: a **manual-only, structured workstream-update record and validation fixture**. Reuse the repository’s maintained status-report content as field vocabulary, not as evidence that an update-collection product already exists. The canonical status report asks users to state reporting period, baseline, source, owner and calculation, and to mark unavailable values unknown; the weekly template already groups progress, blockers, completed work and next steps. Neither defines an individual submission contract, provenance history, stale/missing/conflict rules or duplicate handling.

Defer language extraction until the manual contract and a fixed, owner-approved evaluation fixture exist. Keep channel acquisition in #376 and reminders/escalation in #377; their October 30 research PRs are open, not accepted delivery. Preserve the accepted #1482 walkthrough and #1379 source-sufficiency finding; neither is repeated here.

The repository and issue establish useful artifacts and hypotheses, not observed user outcomes, extraction accuracy, adoption, effort savings or feasibility in a selected application. No live collection, external product/API behavior, participant research or project-board state was tested. Michael should decide whether to promote the manual-only slice and resolve its field, provenance/privacy, staleness and application-surface questions. This report does not select a sprint or alter the epic’s unscheduled status.

## Candidate issue draft — not created or selected

**Title:** Define and validate the minimal workstream-update schema and source contract

- **User outcome:** A PM’s manually supplied update can be represented as a comparable, versioned record for a named workstream/reporting period, with an explicit incomplete/unknown state and enough provenance for review; downstream work can validate it before integration.
- **Scope:** Define one versioned manual-source record contract and synthetic examples; agree required/optional/unknown fields; specify provenance and duplicate/conflict rules; record how `as_of` and missing/stale state are represented; map the contract assumptions to #366/#367 evidence before any integration.
- **Exclusions:** Intake UI, language extraction, Slack/Teams/email/GitHub/Jira ingestion, prompts/reminders, escalation notifications, risk/sentiment prediction, analytics, project timeline synchronization, external/internal summaries, telemetry and production or sensitive-source data.
- **Observable acceptance criteria (proposed):**
  1. Owner-approved schema distinguishes required, optional and unknown fields and includes workstream, reporting period, `as_of`, submission time, submitter/source type and contract version.
  2. A manual-only synthetic example validates against JSON Schema Draft 7; missing required values remain incomplete/unknown and are never inferred as zero or “on track.”
  3. The contract documents the duplicate key, conflict preservation/reconciliation, and how staleness is represented; its stale threshold and resolution authority are owner-approved rather than guessed.
  4. A source/dependency note identifies the exact #366 input-contract artifact and records which #367 assumptions/findings are reused; unavailable evidence remains an explicit open dependency before integration.
  5. Owner-approved source-use, notice/consent and retention/deletion boundaries are documented before any real content is processed; the schema/examples use only synthetic data.
  6. The contract identifies missing/incomplete updates with stable workstream/period/source identifiers for a later #377 handoff; it does not select recipients, channels or send notifications.
- **Validation method:** Draft-7 validation for the synthetic payload plus a table-driven documented fixture for missing, duplicate, conflict and stale states; reviewer checks source/version/provenance and links to the #366/#367 evidence. No Draft-7 validator is integrated at the repository root; the candidate must identify an available validator or separately scope dependency/tooling review. Do not use real project updates or treat passing validation as owner acceptance.
- **Dependencies / owner gaps:** Michael confirms the user task, field/status vocabulary, source/consent and retention boundaries, stale threshold and conflict authority. Verify the exact #366 contract source (the reported development repository was not accessible) and consume #367’s work in PR #1599 before integrations. #369 consumes validated #368 updates; #376 owns channel bots; #377 owns reminder/escalation rules. No #368 child issue or collector implementation was found/created.
- **Effort range:** **Provisional 1–3 engineering person-days, not an approved estimate.** Assumes schema and synthetic fixtures only, a Draft-7 validator/test harness already available in the selected implementation context, one bounded owner review, and no app/store/auth/integration work or real data. If validator/tooling must be introduced, re-estimate and review the dependency separately. Confirm with the owner/engineer before sprint readiness.
