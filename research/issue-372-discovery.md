## Decision brief

Recommend revising #372 from a broad automation/integration epic into a decision about one bounded, template-based UAT traceability and evidence packet. The current curated assets already cover requirement-to-test IDs, scenario steps and expected results, actual results/status, defect IDs, and acceptance roles. The gap is that these fields are split across documents: evidence references and an unambiguous planned-versus-executed coverage denominator are not consistently joined to each requirement/scenario, and the approval authority remains a role placeholder. No maintained evidence here demonstrates automated scenario generation, live GitHub/Jira linkage, real-time execution tracking, or completed UAT.

Use the proposed synthetic fixture below to define what a planning artifact could show, not to claim test execution. Preserve #1482 as completed contributor/maintainer journey validation; it is not formal UAT and must not be repeated. Preserve #1379's accepted source-sufficiency evidence; its independent review and comparative-value gates remain separate and outstanding. The owner must decide whether to promote the template-only slice, keep #372 unscheduled, or defer it. No release or capacity decision is implied.

## Proposed synthetic worked example — planning fixture only

**Not executed UAT.** This fixture defines a proposed review of a UAT packet using fictional requirements and values; it does not test a product or establish acceptance.

| Requirement baseline (2 approved, in-scope functional requirements) | Planned scenario | Type | Expected observation | Proposed record state |
|---|---|---|---|---|
| `REQ-SYN-01`: A user can submit an expense with a positive amount and receive a confirmation. | `TC-SYN-01`: Submit a fictional expense of `$42.50`. | Positive | Submission is accepted and a confirmation reference is shown. | Planned; no actual result or evidence. |
| `REQ-SYN-01` | `TC-SYN-02`: Submit an amount of `$0.00`. | Negative | Submission is rejected with a clear validation message; no confirmation is created. | Planned; if an execution later contradicts expectation, the human tester records the observed result and links an actual defect (example placeholder `DEF-SYN-001`, not a real issue). |
| `REQ-SYN-02`: A submission dated on the final inclusive day of the agreed reporting period is eligible. | `TC-SYN-03`: Submit a positive amount dated 2026-09-30 for a fictional reporting period of 2026-09-01 through 2026-09-30. | Edge | The final-day submission is accepted. Boundary inclusivity must be specified in the project requirement before a real test. | Planned; no actual result or evidence. |

**Coverage definitions for this fixture**

- Requirement baseline `N_req = 2`: approved functional requirements in the agreed scope and baseline version. Excluded, rejected, changed, nonfunctional, and unknown requirements are reported separately, not silently counted as covered or removed.
- Planned mapping coverage = baseline requirements with at least one linked planned scenario ÷ `N_req` = `2/2 = 100% planned`. This is a traceability property, not test execution or pass rate.
- Executed requirement coverage = baseline requirements with at least one executed, evidence-referenced scenario ÷ `N_req` = `0/2 = 0% executed` in this unrun fixture.
- Scenario execution coverage = executed scenarios with an actual result ÷ planned scenarios = `0/3`. Pass rate is **not applicable** because no scenario was executed. If a denominator is zero or unavailable, report “N/A/unknown,” never 0% or 100% by default.
- For any future real execution, capture requirement/scenario IDs, baseline/revision, environment/build, tester/role, timestamp, actual observation, evidence reference, outcome, defect link where applicable, retest link, and authorized human acceptance decision. `DEF-SYN-001` remains a placeholder; no issue is created by this example.
- The acceptance authority is **not named** in this fixture. A project owner must name the authorized human decision-maker. Scenario generation or artifact review cannot sign off.

## Bounded candidate issue draft — for owner selection only

**Proposed title:** Define and validate a UAT traceability and evidence packet using maintained templates

- **User outcome:** As a UAT coordinator, I can prepare a reviewable packet that traces each approved in-scope requirement to planned scenarios, records execution evidence and defect references, and presents the result to a named human acceptance owner.
- **Scope:** Align the existing canonical UAT plan and RTM around one small synthetic fixture; add/clarify evidence-reference, baseline, execution-status, denominator, defect/retest, and named-approval fields only where needed. Keep planned scenarios distinct from executed cases. Preserve manual human review.
- **Exclusions:** Automated generation, persona inference, live GitHub/Jira integration, automated defect creation, dashboards/telemetry, participant outreach, actual UAT execution, sign-off, audit/compliance guarantees, restricted or original-file intake, and product release.
- **Observable acceptance criteria:**
  1. Every synthetic approved in-scope functional requirement has a stable ID and at least one linked planned scenario with type, preconditions, steps, and expected result.
  2. The packet reports planned mapping and executed evidence coverage separately, names the exact denominator and baseline, and represents zero/unknown denominators as N/A/unknown.
  3. An unexecuted scenario cannot be represented as passed; an executed failure can carry an actual issue reference and retest state without implying automatic issue creation.
  4. The packet identifies the human acceptance role and records the actual decision, decision date, and evidence reference only when a person authorized for that project supplies them; placeholders remain visibly unapproved.
  5. A reviewer can trace the synthetic fixture from requirement through scenario, evidence placeholder, defect placeholder, and acceptance decision field without interpreting any fixture value as real execution.
- **Validation method:** Review the completed synthetic packet against the criteria above; independently check each ID mapping, numerator/denominator arithmetic, zero-denominator handling, and planned/executed state; run repository Markdown-link checks. This validates the artifact contract only, not UAT or human acceptance.
- **Dependencies and owner gaps:** Michael Richard decides whether this slice is wanted and names the actual delivery owner/acceptance authority. Confirm the authoritative requirement baseline and issue-reference convention before use. The old #367/#370 dependency wording is historical and must be confirmed if relevant; no live integration dependency is assumed for this template-only slice.
- **Illustrative effort range:** 2–4 person-days, low confidence and not a team estimate or commitment. Assumes one maintainer revises/reconciles the existing docs, a reviewer checks the synthetic packet, and one owner review; excludes user research, software, connectors, actual UAT, and permission work. Re-estimate before backlog selection.

**Disposition of historical claims:** Keep “95%+ functional requirement coverage” as an unvalidated historical target, not a current acceptance result; do not adopt it as a threshold until the source baseline, eligible requirement denominator, exclusions, measurement procedure, and responsible reviewer are agreed. Preserve the effort-reduction and quality-improvement hypotheses separately; no baseline or comparative measurement is present. Methodology adaptations, personas, integrations, real-time reporting, defect automation, and analytics remain unselected scope pending a distinct user outcome and feasibility decision.
