## Decision brief

Retain #105 as an unscheduled candidate, but revise its historical implementation assumptions before selection. Monte Carlo schedule analysis samples durations through a dependency network; it is not, by itself, trained ML. Historical data can help estimate distributions and assess out-of-sample calibration, but is not inherently needed to run a simulation whose inputs come from approved estimates or elicitation. TensorFlow and model training are not prerequisites for that bounded approach.

At base revision [`8078fdd`](https://github.com/mirichard/pm-tools-templates/tree/8078fdd24db8e9d274a5922c1db00c051f708663), the catalog’s canonical schedule template and maintained risk-analysis guidance describe schedule inputs and Monte Carlo concepts, not a validated executable engine. The preserved AI recovery record says schedule outputs were simulated, the risk model was untrained, and no representative evaluation set or agreed calibration criteria existed. Recovery remains paused under #1329. The current #523 direction leaves #105 unselected while #1379 proceeds.

Recommend that Michael decide whether to retain a **standalone, single-milestone forecast** candidate, or defer it pending a later architecture choice. If retained, compare a deterministic CPM finish with an explicitly defined P80 commitment date; disclose calendars, correlation and resource assumptions. The historical “70%+ accuracy” criterion is undefined and should not gate work as written: preserve it as history, then have the owner replace it with agreed out-of-sample calibration criteria or explicitly retire it. No operational forecasting capability, calibration, or user value is established here.

## Synthetic worked example and validation fixture

**Purpose:** compare one explicit decision: use the deterministic CPM finish or a modeled P80 finish when communicating a single milestone commitment. This is a synthetic illustration, not user research, a production-engine result, a calibration study or human acceptance.

**Network and assumptions**

| Activity | Predecessor(s) | Duration input |
|---|---|---|
| A | — | Uniform 2–4 working days |
| B | — | Uniform 3–5 working days |
| C | A (finish-to-start) | Fixed 2 working days |
| D | B (finish-to-start) | Uniform 2–4 working days |
| E (final integration work) | C and D (finish-to-start) | Fixed 1 working day |

Durations are continuous workday units on a standard five-day, eight-hour weekday calendar, with no holidays, date constraints, lags, resource limits or resource leveling. The three random durations are independent **for this fixture only**. A and B begin together; E begins after both paths finish. The forecast milestone is reached when E finishes: `max(A + C, B + D) + E`.

**Deterministic CPM comparator:** use the listed fixed durations and the midpoint of each uniform range (A=3, B=4, C=2, D=3, E=1). Path A–C is 5 days; path B–D is 7 days; E adds 1 day. The CPM finish is **8 working days**.

**Executed illustrative calculation:** using Python 3.12.3, `random.Random(105)`, 1,000,000 iterations, independent `uniform` draws for A, B and D, and linear interpolation of the sorted sample quantiles, the observed mean was **8.004694**, P50 **7.998594**, and P80 **8.734660** working days. The result illustrates that choosing a modeled P80 rather than the point-estimate CPM finish adds about **0.735 working days** in this synthetic network. It does not establish that either date is calibrated or appropriate for a real project.

**Independently checkable proposed tests (not run against an application engine):**

1. Fixed-duration input A=3, B=4, C=2, D=3, E=1 returns exactly 8 working days.
2. Lower-bound durations A=2, B=3, C=2, D=2, E=1 return 6; upper-bound durations A=4, B=5, C=2, D=4, E=1 return 10. Every simulated finish must be within `[6, 10]`.
3. A=4, B=3, D=2 makes A–C the controlling path and returns 7; A=2, B=5, D=4 makes B–D controlling and returns 10.
4. Repeating an identical input, sampler/version and seed reproduces the same run. Record the input hash, RNG/sampler version, seed and iteration count; do not promise cross-version reproducibility without pinning the algorithm.
5. A separate proposed convergence check doubles iteration batches and compares P50/P80 across multiple independent seeds. Estimate quantile uncertainty with documented order-statistic bounds or a bootstrap over independent batches. Candidate rule for owner/engineering approval: require successive P50/P80 movement and a 95% Monte Carlo uncertainty interval for each estimated quantile to be no wider than 0.1 working day, or report non-convergence. This tolerance is proposed, not agreed.

**Forecast interpretation:** P80 is the 80th percentile of the modeled outcome distribution: under the stated assumptions, 80% of simulated finishes are at or before that date. It is not a 95% confidence interval. A confidence interval around the *estimated P80* would describe Monte Carlo sampling uncertainty and must be shown separately if needed. If the date is rounded to a day, disclose the rounding rule and recompute/report the implied coverage.

**Correlation, calendar, resource and calibration limits:** the independent draws are deliberately simple and must not be generalized. Shared risks can make activity durations correlated; any future model needs documented common risk drivers or elicited correlation assumptions and sensitivity analysis, not invented coefficients. Real dates require explicit work calendars, holidays, shifts and lags. Resource-constrained forecasts require availability and a leveling policy; this fixture has neither. An out-of-sample calibration study would need authorized, representative, completed project schedules with forecast snapshots frozen before actual outcomes, project-level holdout separation, declared milestone/horizon definitions, and observed coverage for each selected percentile (for example P50/P80), with uncertainty intervals. No such dataset, permission, sample-size plan or agreed acceptance threshold was found here; no calibration check was run.
