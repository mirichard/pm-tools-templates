## Conditional evaluation design — only after owner selection

### Data, target, provenance, and leakage

Before any acceptance holdout is accessed, the owner and reviewer should record:

1. **Claim and unit:** project population, prediction time, future event, horizon, category definitions, intended decision, and whether the model predicts an ordinal category, event risk, or calibrated class probabilities. Define the unit of analysis and how multiple snapshots of one project are handled.
2. **Permission and provenance:** named data owner, source/version and immutable hash, permitted use, collection period, transformations, label source and rubric, missingness/exclusion rules, and representativeness limits. Use only data already permitted for this purpose; this assignment authorizes no new rights, sensitive/original-file intake, or participant outreach.
3. **Observed labels:** record outcome evidence as of the specified horizon; identify labelers, independence from model outputs, adjudication/disagreement method, and label availability time. Random/synthetic labels and hand-authored scenarios may test plumbing only.
4. **Leakage controls:** freeze a feature-availability cutoff at prediction time. Exclude post-cutoff status, completion/actual outcome fields, later comments/activity, duplicate records, and any label-derived proxy. Keep all snapshots and related records for one project (and, where applicable, one organization/source group) in one split. Fit imputation, scaling, feature selection, calibration, and tuning on training/development data only.
5. **Held-out design:** separate training, validation, and one locked acceptance test by independent project groups. Use a later-time test only if source timestamps and label timing are verified; without reliable dates, call it project-held-out retrospective evaluation, not prospective forecasting. Freeze the split identity and membership digest before score inspection. Do not reuse the already-inspected JOSSE test partition.
6. **Adequacy and coverage:** report class counts by split and supported subgroup before test access. Owner/reviewer must decide whether coverage can support the proposed gates; if rare classes or uncertainty make this impossible, report the limitation rather than weakening criteria after results.

### Baseline, metrics, calibration, variability, and errors

These are **metric candidates and rationale for approval**, not agreed thresholds:

| Evaluation question | Candidate evidence | Threshold rationale to approve in advance |
|---|---|---|
| Does the classifier distinguish the four defined outcomes? | Confusion matrix, per-class precision/recall, macro-F1 or balanced accuracy; report ordinary accuracy as a secondary summary, especially if classes are imbalanced. Consider an ordinal error summary only if the owner approves the category ordering and error costs. | Select the primary metric and numerical acceptance floor based on the decision supported and class prevalence. Explicitly decide acceptable misses of high/critical outcomes versus false alarms; do not infer a floor from existing fixtures. |
| Is it better than a simple reference? | At minimum, a training-set majority/prevalence baseline. Also compare with a versioned current candidate or deterministic rule baseline only if the owner selects it and it can be mapped to the same target without changing its meaning. | Freeze baseline, comparison metric, and any minimum meaningful improvement before holdout access. No improvement or inconclusive uncertainty is a valid result. |
| Do confidence values mean what users may infer? | If a four-class probability vector is retained, report per-class reliability plots plus a multiclass proper score such as Brier score or log loss. If only maximum-class confidence is supported, separately assess calibration of correctness at that confidence; it is not calibration of event risk. | Approve the probability semantics, calibration method/summary, sample-coverage rule, tolerance, and abstention behavior. Do not treat confidence fixtures or accuracy as calibration. Brier score alone mixes calibration and discrimination. |
| How stable and generalizable is the result? | Report project-group bootstrap intervals for primary metrics and paired model/baseline differences; show project-level results/distribution. If a stochastic training process is later selected, report seed sensitivity on development data and lock the final artifact before test evaluation. | Agree the uncertainty interval and decision rule before unblinding. Account for the independent project/group—not correlated task rows—as the resampling unit. |
| Where does it fail or abstain? | Predeclare supported, permissioned subgroups and edge cases; report denominators, class coverage, errors, calibration, missing/conflicting/stale inputs, out-of-domain examples, and high-confidence errors. Show insufficient subgroup sample size as unknown, not as a pass. | Set any subgroup gate and fallback/abstention criteria before results. Do not make claims about groups for which permitted evidence is absent. |

Scikit-learn's official [probability calibration guide](https://scikit-learn.org/stable/modules/calibration.html) is cited only as method background: calibration compares predicted probabilities with observed frequencies, and a Brier score is not a calibration-only measure. Its page was returned by web search on October 30, 2026; direct page retrieval was blocked in this session. No library, implementation, or external acceptance policy is selected here.
