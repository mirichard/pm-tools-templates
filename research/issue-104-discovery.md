## Decision brief

Reuse #1559 to define a source-backed corpus and acceptance fixtures; do not create another implementation story or start #1560. The maintained GitHub Pages source is an Astro static site. Its homepage searches 148 catalog entries by title and description, not document bodies; its placeholder also promises tags that the filter does not search. A separate Express preview demo filters paths across 802 Markdown files in an allowlist, and the CLI selector filters catalog metadata. None is unified full-document search. The repository has 1,531 tracked Markdown files, but 729 fall outside that demo allowlist; tracked generated site output and repeated content make a raw recursive scan an unsafe corpus definition.

Provisionally evaluate a build-time static index first because the deployed site is built as static Pages output; compare a browser-loaded prebuilt index and an API/hosted index on the same corpus and workload. This is an option to test, not a product or architecture approval. Recommend retaining the user outcome, single query, ranking, snippets, mobile/keyboard and sub-500ms criteria while defining measurable boundaries in #1559. Do not treat the historical 95% relevance, 80% time reduction, 70% usage or analytics criteria as achieved or waived: all need an explicit owner disposition. Relevance judgments, telemetry permission, time-baseline method, corpus boundary and capacity remain unresolved. The owner decision is whether to approve the proposed corpus/metric boundaries and authorize any later implementation; this report does not select or promote delivery work.

### Reproducible validation proposal

**Proposed, not executed:** freeze the accepted source manifest and its commit/hash; identify each result by canonical source path and source revision; record generated/alias exclusions. Build the production static artifact from that revision. Run a fixed fixture of 30 queries spanning exact title, body-only phrase, metadata/tag, multi-term, acronym/hyphen, typo (only if supported), duplicate/canonical destination and no-result cases. Record owner-approved graded judgments before examining rankings. For each query, verify expected relevant documents, ordering metric, snippet source/escaping and destination.

For latency, capture browser/version, runner/device, viewport, corpus and compressed index size. Test the same 30 queries five times after a cold page/index load and five warm repetitions; measure from committed query input (including any debounce) to the first completed result render. Report p50/p95 for warm queries and cold load/search separately. Run the same fixture at desktop and agreed mobile viewport; the viewport alone is not device-performance evidence. A proposed threshold is p95 ≤500 ms for warm query-to-render, but the issue specifies neither percentile nor boundary, so owner approval is required before this becomes acceptance. Do not report synthetic checks as human usability or outcome validation.
