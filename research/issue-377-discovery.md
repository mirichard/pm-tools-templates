## Decision brief

Recommend that Michael consider one bounded first slice: an owner-configured, deterministic reminder eligibility policy with a preview-only evaluator and synthetic audit fixtures. Do not begin with machine-learned timing, channel preference, or live delivery. The reviewed Actions workflows demonstrate schedules, configurable manual runs, email, and risk-issue creation, but they do not establish an approved recipient list, task-level thresholds, quiet hours, cancellation, deduplication, or a reminder audit contract. They are examples to compare, not a reusable reminder service or proof of successful behavior.

The evaluation should return an explicit decision and reason for each task/threshold: eligible, deferred, cancelled, or suppressed. It should use only explicit owner-approved recipients and escalation paths; absent or ambiguous policy means no delivery. Use a named time zone and define quiet hours before any future delivery. GitHub documents time-zone support for scheduled workflows, but scheduling mechanics cannot resolve policy or guarantee that a run executes at an exact minute.

The source evidence is repository/workflow review, not runtime verification, user research, or measured outcomes. The 95% response-improvement target and other historical feature claims remain unvalidated business hypotheses; they need a denominator, baseline, measurement window, and privacy decision before becoming acceptance criteria. Michael must decide whether to promote the preview-only slice and approve its policy inputs. This report does not select a sprint or change issue status.

## Proposed synthetic worked example / validation fixture

**Synthetic policy fixture `SYN-RM-01` — proposal only.** No production task, recipient, clock service, notification, or project data is used.

| Input | Fictional fixture value |
|---|---|
| Task | `TASK-042`; status `open`; no suppression flag |
| Due time | `2026-11-06T17:00:00Z` |
| Policy | Reminder threshold `24h`; recipient `user-A` explicitly marked approved; time zone `America/Los_Angeles`; quiet hours `21:00–08:00` local |
| Evaluation | `2026-11-06T15:30:00Z` (`07:30` local, after the 24-hour threshold) |
| Expected preview | `deferred_quiet_hours`; earliest permitted evaluation `08:00` local. No message is sent. |
| State change before next evaluation | Task becomes `completed` at `07:45` local. Expected result: `cancelled_completed`; do not emit the pending reminder. |

**Proposed tests, not executed:** evaluate each case as a pure decision with a stable task/policy/due-revision/recipient-set-revision/threshold key; repeat the same evaluation and expect one logical action; move the due time and expect the old pending decision cancelled and a new revision evaluated; change the approved recipient set and expect the old pending decision cancelled and a new key; remove recipient approval or the time zone and expect a no-send suppression reason; cross the quiet-hour boundary and a DST transition; test escalation only with a separately approved recipient and threshold. Every fixture should assert both decision and reason, including a no-action case.

**Audit fields proposed for review:** synthetic task key, policy version, due-time revision, recipient-set revision, threshold, evaluation timestamp and named zone, eligible recipient reference (not message contents), decision/reason, and idempotency key. Retention, recipient-reference format, and whether a future implementation persists this record are unapproved.

**Executed evidence:** repository file/issue/PR review and the checks reported below only. No workflow, reminder, escalation, live integration, evaluator, external product, or human acceptance test was executed. **Human acceptance:** pending Michael's decision; the fixture and expected results are proposals.

## Candidate issue draft — not created or selected

**Title:** Define and preview deterministic task-reminder eligibility

- **User outcome:** A PM can preview, for a task and an approved policy, why a reminder/escalation would be eligible, deferred, cancelled, or suppressed—without sending it.
- **Scope:** Owner-approved rule inputs; deterministic threshold evaluation; explicit recipient mapping; named time zone and quiet-hour calculation; cancellation/deduplication rules; decision reasons and synthetic fixtures.
- **Exclusions:** Live email/chat/SMS, bot installation, telemetry or behavioral monitoring, inferred recipients/preferences, ML timing/channel selection, production persistence, and changes to sprint/milestone commitments.
- **Observable acceptance criteria (proposed):** Every fixture returns the expected decision and reason; identical input is idempotent; completed/cancelled items do not remain eligible; due-date/recipient-set/policy changes invalidate the old pending key; each recipient is evaluated independently using the explicitly approved time zone and quiet hours; DST cases use the named zone; missing owner-approved policy values never generate an eligible send. Human review confirms the policy before this candidate is considered complete.
- **Validation method:** Table-driven unit tests for the synthetic cases above plus a preview-only output review. Any future workflow integration requires separate permission/security and delivery tests; passing fixtures is not owner acceptance.
- **Dependencies / owner gaps:** Michael must choose task/status source, recipients and escalation paths, threshold/grace values, time zone and quiet hours, cancellation/suppression rules, and audit/retention boundary. Confirm the #368 input/status contract and coordinate any chat/channel transport with #376; #371 may inform role/cadence terminology but does not approve recipients.
- **Effort range:** **Provisional 2–5 engineering person-days, not an estimate or commitment.** Assumes policy values are supplied, a preview-only evaluator and tests in an existing test environment, one task/status input shape, and no integration, storage, permissions, or real data. Re-estimate if those assumptions do not hold.
